## M1：検査の再現性

期待値はfixture側、実判定はcore側に分けます。
期待値の改変で必ず不一致を検出し、内容拒否が期待どおりならcheckは成功します。
上流の最初の理由を保存し、検査器が返さない位置情報・全検査合否を追加しません。

完了の証拠は、固定rev、lockfile、入力一式、5ケースのreport.json、
不一致・入力エラー・保存エラー・既存出力保全の試験結果です。
体験HTMLの有無だけでM1を評価しません。

## M2：表示の正しさと操作

index.htmlを直接開き、左・中央・右の対応を追えることを確認します。
理由と注釈の意味が違う場合は、単にレイアウトが整っていても未完了です。
不一致の画面では古い理由の強調を外し、実判定と期待を併記します。

完了の証拠は、全ケースのDOMとreport.jsonの一致、2回生成時の成果物一致、
ネットワークなしの閲覧、SafariとChromium系での確認、日本語とキーボード・拡大表示の記録です。
OSやブラウザ版を実測範囲より広く一般化しません。

## M3：第三者の再実行と説明

既存のRust/rustupだけを前提にした手順で、別の人が固定したlabの変更一式から実行します。
初回の依存取得が必要なことを明示し、隣のleak-fence checkoutを要求しません。
説明の途中で実装者が操作を代行した場合は、その介入を記録します。

確認する問いは次の3つです。

1. JSONと項目が正しくても、他テナントの行を返せないのはなぜか。
2. 同一テナントでも未許可IDを拒否する必要があるのはなぜか。
3. このデモが確認していないことと、自分のAPIで次に行う検査は何か。

回答と詰まりを事実として記録し、恣意的な点数・時間・人数で成功率を作りません。
協力者不在なら、クリーン配置での自己確認までを記録してM3を未完了にします。
実装中に第三者へ自動連絡したり、公開して協力者を募集したりしません。

## 継続・縮小・中止の判断

| 状況 | 次の判断 |
| --- | --- |
| 上流coreを固定revでそのまま利用できる | 最小構成でM1へ進む |
| ハイライトに上流の診断API変更が必要になる | 作者注釈に戻す。自動位置特定は別件 |
| 3日相当でも正しい3列比較に届かない | メディア作成を止め、既存CLI + 静的比較へ縮小案を出す |
| 第三者が差を理解できない | ケースを増やす前に、左列・理由・注釈の説明を一度修正する |
| 既存CLIだけで同じ理解・導入が得られる | ラボの追加機能を止め、説明資料として残す |
| ラボは理解されるが導入行動につながらない | 導入負担・対象ユーザーの問題を切り分け、機能追加で解決したと見なさない |
| 任意入力、プロキシ、日次枠、クラウドの要望が出る | 主目的への必要性と費用を別に評価し、合意前に実装しない |

README画像・GIFの完成を、利用者理解より優先しません。
公開や販売へ進む場合は、対象成果物・版・内容をレビュー可能にしてから、その操作の承認範囲を確認します。
