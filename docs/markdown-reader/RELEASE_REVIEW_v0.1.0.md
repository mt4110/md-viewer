## 優先指摘

P1は公開前に解消する項目、P2は公開対象・制約を明確にしたうえで対応を決める項目とする。
セキュリティ指摘と配布成立条件は区別する。

### P1：特殊ファイルで読込処理が停止する

根拠：reader/src/document.rsのread_boundedはFile::openの後でis_fileを調べる。
そのためFIFOは通常ファイル検査に到達する前にopenで待機する。実原稿にも画像にも同じ関数を使う。

再現：専用の一時フォルダー内にpipe.md、pipe.pngのFIFOを作り、実Rustレンダラーへ渡した。
どちらも2秒で戻らず、試験用子プロセスをタイムアウトで終了した。アプリ全体のフリーズやコード実行を再現したわけではない。
読み込みワーカーを占有し、原稿が開けなくなる問題である。拡張子・バイト上限はこの待機を防がない。

必要な修正：アクセス前に特殊ファイルを拒否し、Unixでは検査とopenの間の置換でもFIFO待機しない開き方を選ぶ。
メタデータの事前確認だけを追加して競合対策完了とは扱わない。
文書・画像両方のFIFO、リンクや更新での再読込、通常ファイルが通ることを回帰テストに加える。

### P1：WindowsのUNC拒否が初回読込に適用されない

根拠：session::valid_pathではWindowsのUNCを拒否するが、ファイル選択・CLI・ドロップ等はreceive_atからloadへ進む。
load_modeはパス種別の拒否より先にcanonicalizeを行い、valid_pathを通していない。

これは静的確認であり、WindowsでSMB通信・認証の発生を再現してはいない。
ただしUNCを渡すと、アプリの拒否判断より先にOSのネットワークファイルアクセスへ到達し得る。
「確認前に自動アクセスしない」という方針では、WebのURLだけでなくファイルの入口もそろえる必要がある。

必要な修正：全入口の共通読込層でUNC・デバイスパスをI/O前に拒否する。
リンク・ジャンクション・シンボリックリンクの参照先検査についても境界と限界を明記する。
Windows実機でUNC・拡張UNC・デバイス・ローカルドライブを試す。Macのマウント済みネットワークボリュームまで拒否できたとは主張しない。

### P1：ライセンスが未決定でOSSとしての利用条件がない

リポジトリとreader/にLICENSEがなく、製品Cargo.tomlにもlicense情報がない。
PUBLICで閲覧可能なことと、OSSとして利用・改変・再配布を許諾することは別である。

必要な判断：MITまたはApache-2.0等の利用条件を所有者が決める。
必要な著作権・ライセンス本文、配布物の第三者ライセンス表示を整える。
既存資産の権利を確認せず、一律に新しいライセンスを付けない。
依存のSPDXメタデータに欠落は見つからなかったが、MPL-2.0等もあり、メタデータ一覧だけでバイナリ配布の義務を満たしたとは扱わない。

### P1：配布経路が旧ラボと混在している

通常のルートCargo.tomlはveil-boundary-lab。tools/package_source.pyはreader/を収集せず、旧ラボ名のアーカイブを作る。
READMEでは旧用途と説明しているが、v0.1.0の標準的な取得・ビルド・配布経路にはなっていない。
GitHubには実装自体がなく、現在のmainへタグを付けてもアプリのソースは含まれない。

必要な修正：既存成果物を保全して、md-viewerを既定でビルドする入口、対象ファイルを限定した梱包、クリーンな別配置での再現を用意する。
ソースのみのv0.1.0と、非エンジニア向けバイナリ配布を区別する。
開発用debug .appとad-hoc署名は公開用インストーラー・Developer ID署名・公証の検証ではない。
Windows .exe、macOS .app/.dmgの実配布・導入・関連付け・終了・更新の確認は未完了である。

### P2：画像と復元タブの資源上限が不足している

根拠：画像は単体20M画素と圧縮バイト合計を制限するが、画素合計・画像要素数を制限していない。
約1.9KBのMarkdownで1000×1000画像を100回参照すると、100画像・計1億画素のHTMLを受理した。
出力は535600バイトで、HTMLキャッシュ上限には届かない。
すべてRGBA展開する場合の400000000バイトは計算値であり、ブラウザ使用メモリの実測ではない。
同一画像の共有・遅延展開によって実使用量は変わる。実クラッシュを再現したとはしていない。

またshowでは64MiBのキャッシュ検査があるが、activateの復元経路はrestore_documentの結果を同じ検査なしでtab.docへ入れる。
多くの復元タブを開くと文書化された上限を超えて保持できる。こちらは静的指摘で、最大負荷のメモリ試験は未実施。

必要な修正：画像数・画素合計の予算、すべての読込経路に共通のキャッシュ制限と解放方針を作り、境界・拒否後の継続操作を試す。
「軽量・低消費電力」を数値の根拠なく保証しない。

### P2：テストの入口と自動検証が未整備

Rust19テストとUI3スクリプトは成功した。ただしUIテストはIPCを差し替えており、権限・OSの入口・バンドルは同時には検証しない。
JavaScriptの開発依存を固定して入れるpackage.json/lockと一括チェックがなく、現状の実行は既存Playwright環境に依存する。
GitHub Actions等のCIも未配置で、Windowsを含む第三者環境の再現は確認できていない。

必要な修正：開発専用の依存・実行コマンドを固定し、macOS/WindowsでRustチェック、レンダラー安全性、UI試験、リリースビルドを自動化する。
FIFO・UNC・画像負荷・復元キャッシュの回帰を追加する。署名や対話的な標準ブラウザ起動はCIだけで完了としない。
SECURITY.md、報告方法、対応OS、既知制限、変更履歴を整える。これらはアプリ本体への追加権限を要しない。

## 確認できた防御

- 原稿の生HTMLはエスケープされる。外部画像・フォント・スクリプトを自動取得する実装は見つからなかった。
- CSPはスクリプトをself、画像をdata、接続をIPCへ制限する。汎用のシェル・ファイル操作プラグイン権限は与えていない。
- ローカルリンク・画像は正規化した参照範囲を検査する。ただし競合・ネットワークファイルシステムまでの完全な隔離証明ではない。
- WebリンクはRustでHTTP/HTTPSのみを検査し、認証情報・不可視文字等を拒否する。単回・期限付きの確認済みURLだけをOSへ渡す。
- Windowsの外部リンク起動はShellExecuteExW経路を選ぶコードで、cmd /c startへURLを文字列結合しない。Windows実行は未確認。
- セッションは本文を保存せず、サイズ・形式・位置情報を検査し、原子的に置換する。URLをアプリのログへ保存するコードは見つからなかった。
- 永続化・自動起動・認証情報収集・広告・採掘・遠隔コマンド・テレメトリーの独自実装は見つからなかった。

これは調べたソースに対する判断であり、すべての依存・OS・配布バイナリの無害性を証明するものではない。
通信が少なくても、Markdown・画像・パス・復元データ・OS連携は攻撃入力になり得る。
