# veil-boundary-lab 設計

状態：2026-10-29作成の設計。M2まで実装・ローカル検証済み。M3は未実施。詳細はVALIDATION_M2.md。
M1の結果は[VALIDATION_M1.md](VALIDATION_M1.md)を参照します。

## 1. 目的と価値の仮説

対象は、JSONを返すAPIの開発者と導入を検討する担当者です。
正常なJSONや項目の許可だけでは、レコードを返してよい相手かどうかは分からないことを伝えます。

期待する行動は、正常・別テナント・同一テナントの未許可IDを比較し、
自分のAPIの認可結果と応答を既存LeakFence CLIで確かめることです。
閲覧数やテスト数から需要・購入意思を推定しません。

長期的な目的は、自分のプロダクトから持続的な収益を作ることです。
ラボはLeakFenceの説明・導入の補助であり、独立した新製品として育てる前提を置きません。
現在の主力プロダクトと優先順位は本依頼だけでは未確認です。この作業を別案件に優先するP0とは扱いません。
2〜3日は実装の見積もりであり、期限内の完成や需要を保証する値ではありません。

代替は既存の`leak-fence demo`とREADMEの比較表です。
ラボの追加価値は、認可情報と応答の対応箇所を視覚的に追えることに絞ります。
その説明に効果がなければ、ケースや画面を増やすより既存デモへの説明追加で止めます。

## 2. 元の提案に足りなかった点

| 論点 | 確認した事実・問題 | この設計での扱い |
| --- | --- | --- |
| 違反箇所 | `inspect`は`Result<Cost, Denied>`を返すだけで、位置情報を返さない | 作者が指定した説明箇所として表示。自動検出位置と呼ばない |
| 判定の粒度 | 最初の拒否で終了し、全検査の成功・失敗一覧は返さない | 「項目検査は成功」等を実測として表示しない |
| 期待結果 | 拒否なら何でもよい照合では、別理由の拒否を見逃す | 許可・拒否と理由コードまで完全一致を要求 |
| 入力の保存 | 既存CLIは本文を保存しないが、ラボはHTMLへ本文を保存する | 合成ケース専用。任意入力・アップロードUIを作らない |
| 認可情報の出所 | Contextの正しさは呼出元への信頼に依存 | 左列に「サーバー側の認可結果を模した合成データ」と表示 |
| 検査の限界 | 許可項目の値の意味や由来は判定しない | 制約を示す許可ケースを一つ含める |
| 再現性 | 隣のローカルリポジトリへのpath依存では他人が再実行できない | 公開済みの特定Gitコミットへ固定 |
| 結果の鮮度 | 古いHTMLを最新の再検査結果と誤解できる | 検査器rev・入力・suite版を保存し、更新には再実行が必要と明示 |
| エラー | 検査拒否とラボの読込・保存失敗を混同しやすい | 内容判定、期待照合、実行失敗を分ける |
| オフライン | 初回ビルドと閲覧時の通信は条件が違う | 初回取得は通信あり。取得済み依存での実行とHTML閲覧がオフライン |
| Fixture / Repro | 本依頼から具体的な既存リポジトリ・APIを特定できない | 合成ケース作成・小例の再実行という役割だけ採用。新たな依存にしない |

根拠の詳細は[EVIDENCE.md](EVIDENCE.md)を参照します。

## 3. MVPと対象外

必須の体験ケースは5つです。設定、入力、期待値はすべてレビュー可能なファイルに置きます。

| ID | 体験 | 実際の期待結果 |
| --- | --- | --- |
| `allowed` | 許可された所属・ID・項目の応答 | `passed` |
| `foreign-tenant` | 正常な行の後に別テナントの行が混入 | `denied / tenant_mismatch` |
| `unauthorized-id` | 同一テナントだが許可ID集合の外 | `denied / object_unauthorized` |
| `extra-field` | 所属・IDは正しいが項目が追加 | `denied / unapproved_field` |
| `value-not-classified` | 許可されたnameへ、出所を判別できない合成値が入る | `passed`。値の意味は検査対象外 |

追加項目は`internal_note`等を使い、APIキー風の文字列を主役にしません。
他テナント混入は1行だけの入れ替えではなく、正常行と違反行の混在にします。
同ケースでは混入行のIDを許可集合に含め、違反原因をテナントだけに限定します。
未許可IDケースは所属・項目を正しく保ち、IDだけを変えます。

不正JSON、重複キー、入れ子、空配列、件数・バイト境界、複数違反の先行理由は回帰試験で扱います。
すべてを画面のケース一覧へ追加しません。表示する制約ケースが誤解を招く場合は説明を直します。

今回作らないもの：プロキシ、HTTP API、クラウド配置、認証、DB、日次枠の模擬実装、
任意ファイルの検査UI、Wasm版検査器、PII・秘密検知、Fixture / Reproの汎用基盤、課金、解析通信。
PNGとGIFはMVPの必須条件から外し、正しい画面を確認した後の任意タスクにします。

## 4. アーキテクチャ

単一Cargoパッケージ、ライブラリと一つのバイナリで開始します。
crate分割、非同期ランタイム、DIフレームワーク、プラグイン機構は不要です。

```text
fixtures/demo（原本バイト列 + 認可情報 + 期待結果 + 説明用注釈）
      │
      ▼
fixture.rs ── 読込・構造検証・入力上限・順序
      │
      ▼
engine.rs ─── 固定revのleak-fence-core::inspectを一度だけ呼ぶ
      │
      ▼
report.rs ─── 実判定と期待結果を照合 → SuiteReport
      │                          │
      ▼                          ▼
report.json                 render.rs → index.html
                                 │
                                 ▼
                      ブラウザは生成済み内容を表示
```

`main.rs`は引数、標準出力、終了コードだけを担当します。
`lib.rs`の`evaluate_suite`と`build_report`を統合試験から呼べるようにします。
判定に使う型・関数と、説明・HTML生成に使う型・関数を混ぜません。
結果のDTOはラボが所有し、上流型のSerialize追加をLeakFenceへ要求しません。

### 依存と固定方法

```toml
[dependencies]
leak-fence-core = { git = "https://github.com/mt4110/leak-fence", rev = "6a0f416e23da5e0cff5890fd05b6b1d9a4162393" }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

この依存でCargo.tomlとCargo.lockを作成し、M1をビルド・検証しました。
coreは`publish = false`のためcrates.io配布を前提にしません。coreのコピーも持ちません。
最初の依存はこの3つに限定し、具体的な解決版、ライセンス、既知脆弱性をT01で確認します。
上流のMIT表記を尊重し、コアの転載時には帰属・ライセンスを保持します。
ラボ自身の公開ライセンスは未決定で、依存のMITから自動決定しません。

GitのrevとCargo.lockを追跡し、通常の確認は`--locked`を使います。
CargoによるGit依存とlockfileの扱いは[Cargo公式資料](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html)に基づきます。
初回取得後のネットワーク禁止確認には`--frozen`を使います。
上流更新は別タスクでrev・lock・ケース結果・説明をまとめて見直します。

## 5. 画面と説明の責務

冒頭に「秘密らしい文字列がなくても、返す相手を間違えれば越境する」を置きます。
通常ケースへのリンクと5つのケース一覧、その下にケースごとの3列を並べます。
リンクは同じHTML内のアンカーへ移動し、選択先を`:target`で示します。
最初の版ではタブ風の単一画面切替を作らず、標準のリンクとページ内移動で比較します。

| 左：返してよい範囲 | 中央：APIが返そうとしたJSON | 右：保存済みの検査結果 |
| --- | --- | --- |
| 所属、許可ID、許可項目、操作権限 | 原本のJSON。整形による意味・位置の変更なし | 内容検査の許可・拒否、固定理由、期待照合、説明 |

左列はPolicyだけではなくContextも表示します。生のJSONは補足の`details`から読めます。
日次上限はPolicyの必須設定として残りますが、「この検査では未使用」と添えます。
右列の許可表示は「内容検査に通過」であり、「安全」「本番へ返してよい」と言い切りません。
常に「日次取得枠：未検査」「API通信の遮断：未実施」を併記します。

拒否は応答全体に対する結果です。違反行だけを除いた応答や自動修正案を生成しません。
成功ケースではcostの件数とUTF-8バイト数を表示し、拒否ケースのcostを推測しません。
許可項目の検査は項目名のallowlistであり、name等の必須項目・値の型まで検証するJSON Schemaではありません。
原提案の「JSONとして正しい／項目が許可済み／所属が違う」という比較は、作者の教材説明として記載できます。
検査器が3つの独立した合否を返したようなチェックリストにはしません。

### ハイライト

注釈は原本の行範囲と期待する行テキストを作者が指定します。
Rust側が該当行と文字列の一致を確認し、HTML escape後に`mark`を付けます。
行全体の強調をMVPとし、JSONパス解決・トークナイザー・文字オフセットの推定は作りません。
1行1項目の整形済みfixtureを使えば、項目の強調として読めます。
左列と中央の注釈に同じ説明IDを付け、右列の理由からアンカーで参照できます。
「説明用の強調。検査器は位置情報を返しません」と表示します。

実判定が期待と不一致のときは、拒否理由に結び付ける注釈を非表示にします。
存在する行だからというだけで、実際の拒否原因を証明したことにはしません。
不正JSON等、位置を説明できない回帰入力は注釈なしで検査できます。

### 読みやすさと操作

広い画面では3列、狭い画面と文字拡大時には左→中央→右の順に縦積みします。
JSONブロックだけを横スクロール可能にし、ページ全体の横はみ出しを避けます。
見出し・通常リンク・details・markを使い、色以外に理由と説明IDを表示します。
キーボードのフォーカス、200%拡大、日本語、長いID、読み上げ順を確認します。
常時アニメーション、スムーズスクロール、外部フォントは不要です。
JavaScript無効時を通常状態とし、JavaScriptを使わないこと自体を正しさの証明とはしません。

## 6. 保存・失敗・安全性

結果、原本本文、Context、Policy、説明はすべてローカルの成果物へ保存されます。
ラボは実データを受け付ける汎用ツールとして案内しません。
合成データという作者の宣言だけで、秘密が含まれないことを技術的に保証できるとは説明しません。
公開前にはfixtureと出力を人が確認します。

ブラウザ用HTMLは単一ファイルとし、fetch、外部script・画像・CSS、解析、保存領域を使いません。
外部リンクへの利用者の明示操作を除き、閲覧時の通信を必要としない構成にします。
入力由来の表示文字列はHTMLテキストとしてescapeし、HTML・属性名・URL・CSSとして挿入しません。
例外としてDOM参照用のケースID・注釈IDは`[a-z0-9-]{1,64}`に限定し、固定の形式で属性へ使います。
テンプレート先頭にCSPのmetaを置き、少なくとも`default-src 'none'; script-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'`を指定します。
inline CSSの許可は固定CSSのためです。fixture由来のstyle属性やCSSを許可する設計ではありません。
CSPだけに依存せずescapeとブラウザでの攻撃文字列表示も確認します。
CSPのスクリプト制限は[MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src)を参照しています。

`build`は存在しない出力ディレクトリだけを受け付けます。既存ディレクトリの置換・削除・自動清掃はしません。
親ディレクトリは必要なら作成し、既存の親とその内容は保全します。最終出力ディレクトリ自体は新規作成に限定します。
入力と注釈を全件検証し、実検査と照合を終えてからファイル生成を始めます。
`report.json`を先に、`index.html`を最後に`create_new`で書き、両方の書込・flush成功後だけ成功を返します。
途中で失敗した成果物は残し、未完了と出力先だけをstderrへ示します。別の出力先で再実行します。
2ファイルの原子的な確定や耐電断性は保証しません。途中失敗した出力を公開用に使いません。

期待値の不一致は保存可能な検査結果です。HTML冒頭にも不一致を表示し、終了コード2を返します。
ファイル読込・構造不備・注釈不整合・保存失敗はラボの実行失敗で、終了コード1です。
本文や認可情報をstdout/stderrへダンプせず、固定コードと合成ケースID・出力先だけを出します。

## 7. 成功条件と停止条件

技術的な条件は、固定した実検査器による5ケースの期待一致、改変時の不一致検出、
同一入力からの同一レポート、ネットワークなしの閲覧、第三者による再実行です。
画面の内容判定・理由は必ず実検査結果から作ります。

説明の条件は、第三者が「所属の違い」「同じ所属でもIDが違うこと」「検査しない範囲」を自分の言葉で説明でき、
次に試すCLI手順へ到達できることです。人数や秒数を根拠なく合格点にせず、迷いと操作を記録します。
協力者がいなければ第三者再現・説明の条件は未確認として残します。

上流の変更、診断APIの追加、汎用入力、クラウドが必要になったらMVPから切り離して再見積もりします。
3日相当の作業を超えても最小の比較が成立しない場合は、GIFや装飾を中止し、
既存CLI出力と静的な比較HTMLへ縮小する案をレビューします。基準を弱めて完成とはしません。
